# Design Document

## Context & Scope

Edbot is a pedagogical multiagent system that serves as a self-directed learning tool for students in introductory computer science courses. An experimental research study will assess whether an agent that truly analyzes a student's intentions, mastery level, and understanding of a fundamental concept with tailored responses can engage in conversations that improve a student's learning experience. The control group will be given a baseline agent that does not interpret a student's learning progress, whereas the experimental group will be allowed to use a more advanced multiagentic tool intended to motivate more personalized learning. Students interact with the agent using a chatbot interface, unaware of the multiagentic architecture powering the system. Use of the tool is completely voluntary and students are unaware of the two versions of the agentic tool.

## Goals and Non-Goals

Goals

* The system should comply with FERPA regulations, ensuring the confidentiality and integrity of student data across conversations with all users.  
* Students should be able to freely access all features of the chatbot interface without knowing the underlying architecture of the system.  
* Professors should be able to add or remove course-related content as the system’s source of truth during any point of the system’s deployment.  
* The system should achieve 90% availability.  
* Students should receive responses back from the chatbot in the order of seconds, depending on the scale of their request.

Non-Goals

* The system should not be able to search the web for material.  
* The system should not generate responses without reliable internet connection.

## The Design

### Agentic Architecture

Edbot follows a centralized architecture, powered by an orchestration layer that manages and delegates tasks to specialized subagents. User prompts and interactions are processed only by the orchestrator agent and responses are parsed and formatted by the orchestrator agent before returning back to the user.

### Memory

Each subagent spawns independently of the orchestrator agent without inheriting its context, so the agentic structure requires the Understanding-Checking agent utilizes a shared memory to analyze student responses and interactions with the chatbot.

### Agents

**Orchestrator Agent**  
Purpose

* Sole interface to the student  
* Owns intent classification, concept extractions, subagent routing, and response synthesis  
* Subagents never see raw student text directly, only structured requests from the orchestrator  
* The orchestrator does not generate any CS-concept content itself. All tailored explanations, questions, and probes are generated by the Content-Generating Agent so responses are tier-calibrated

Skills

* Intent Classification  
  * Categorizes each incoming message into a bounded set: new concept inquiry, practice request, answer submission, follow-up/clarification, general explain request, off-topic/other  
  * Includes a short explanation of the reasoning behind the particular intent classification  
* Concept Extraction/Normalization  
  * Maps free-text student language to a concept in the CS concept taxonomy (“recursion”, “big-O”, “pointers”) so subagents get consistent identifiers. The CS concept taxonomy is dynamically built as new resources are uploaded  
* Escalation Decision  
  * Decides whether to invoke the UCA to reassess a concept before generating a response, or trust the existing student-model value  
1. Intent-based hard triggers: answer submissions always escalate, as does a practice request for a concept. Follow-up questions should also trigger an escalation, since they tend to point toward misunderstandings or potential areas of growth  
2. Lightweight model-judged flag: determines if this message contains new evidence about understanding beyond what’s already known. Folded into intent-classification call rather than a separate LLM round-trip  
3. A cadence-based backstop: force a re-check on a concept if nothing else has triggered one in the last 10 (tuneable) turns  
* Subagent Routing  
  * Calls the UCA and/or CGA as tools, based on intent and the escalation decision  
* Scope-Boundary Handling  
  * If a student asks about something unrelated to CS course content, responds that the topic is out of its scope  
* Response Synthesis  
  * Merges subagent outputs into a natural reply, hiding the multiagent architecture from the student  
* Logging Signal  
  * Logs every routing decision, subagent input/output, and state transition for research analysis

Tools

* retrieve\_source – references course material to ensure its response to the student is within the scope of the concepts taught in lectures

Input

* Raw student message  
* Student model (read-only, shared memory)  
* Question-interaction log (read-only, shared memory)

Output

* Input content for UCA or CGA

**Understanding-Checking Subagent**

* Toggled on only for the experimental group

Purpose

* Pure assessment function  
* Given a concept and evidence, estimates the student’s Bloom’s Taxonomy tier for that concept and owns all updates to the student model (read and write)  
* Never talks to the student directly, but receives context on *why* it was invoked (practice request vs follow up)

Skills

* Bloom’s Tier Classifier  
  * Analyzes language, reasoning patterns, and correctness of statements/answers to place the student on the taxonomy  
* Answer evaluation mode  
  * An invocation mode for grading a specific submitted answer against a rubric, distinct from a general conversational assessment  
  * Judging evidence of understanding applied to a narrower input and specified rubric  
* Confidence/Uncertainty Scoring  
  * Flags low-confidence assessments. On low confidence, the orchestrator has the CGA ask a probing follow-up rather than committing to a tier  
  * Serves as a control-flow signal, where control never invokes the UCA, and as a logging metric  
* Evidence Citation  
  * Returns short justification tied to specific things the student said, not shown to student  
* Cold-Start Probing  
  * Drives a binary-search style sequence to establish a starting tier for a concept with no prior assessment (no data in the student-model for this concept)  
  * The CGA generates the actual probe question at each target tier  
  * The escalation trigger continues refining the estimate through normal conversation

Tools

* retrieve\_source  
* fetch\_student\_data – fetches information on student’s mastery level from database, if exists

Input

* Concept (Recursion, Time Complexity, Dynamic Programming, etc)  
* Question the student answered  
* Response the student gave  
* Rubric for the question the student answers (optional, obtained from question-interaction log)  
* Conversation history  
* Student model (shared memory)  
  * Read prior Bloom’s estimate for that concept  
  * Write new Bloom’s estimate for that concept, if changed

Output

* Bloom’s tier estimate   
* Confidence score  
* Brief evidence rationale  
* Updated student-model entry for the concept  
* A correctness/quality judgement against the rubric (optional, if answer was submitted)

**Content-Generating Subagent**  
Purpose

* Content generation function for all CS-concept content, including practice questions, tier-calibrated explanations/follow-up, and cold-start probing questions  
* Everything related to CS content routes through this agent, so tailoring stays centralized and consistent between the control and experimental groups

Modes

* The different modes of the CGA allows the agent to handle different content-generating situations with different behaviors. Each mode is given its own input/output contract, so the CGA knows the shape of what to produce and what to work with  
* generate\_question  
  * Input: concept, target Bloom’s tier (falls to default for baseline model), format constraint (optional: multiple choice, short answer, code-writing, code-tracing), prior questions asked  
  * Output: question text, rubric, metadata (tier, format, concept tags)  
  * Use cases: practice/exam question requests  
* explain\_at\_tier  
  * Input: concept, target Bloom’s tier, last 3 exchanges  
  * Output: tier-calibrated explanation/clarification/follow-up response  
  * use cases: follow-ups and general explain requests  
* probe\_at\_tier  
  * Input: concept, target tier (direction chosen by the UCA’s binary search)  
  * Output: a conversational probing question at that tier (lighter-weight than generate\_question)  
  * Use cases: cold start, when no prior assessment exists for a concept

Skills

* Tier-Calibrated Generation  
  * Templates/prompting strategy per Bloom’s tier (e.g. Remember \-\> definition recall; Apply \-\> code trace/predict output; Analyze \-\> debug/compare approaches; Create \-\> design a solution)  
  * Applies across all three modes above  
* Format Selection  
  * Chooses question/response format appropriate to concept and tier   
* Novelty check  
  * Avoids repeating recent questions for the same concept/student. Sources from the question-interaction log from shared memory  
* Answer key/rubric generation  
  * Produces a scoring rubric alongside each generate\_question output, so the UCA has something concrete to evaluate against later

Tools

* retrieve\_source  
* retrieve\_question\_bank  
* MCPs for BruinLearn, GradeScope (if possible, but unlikely due to student privacy concerns)

## Alternatives

#### Single and Multi-Agent Systems

Single agent systems rely on one autonomous AI model and a preconfigured system prompt to plan, brainstorm, and execute tasks from start to finish. They are responsible for utilizing their own tools, calling functions, and making decisions based on the user’s query. We start to look beyond a clearly defined program using APIs when the goal we want to achieve requires multiple steps and workflows are open-ended problems. 

In contrast, a multi-agent system uses more than one agent, where each agent handles delegated subtasks either sequentially or in parallel. Multi-agent systems are ideal for larger workloads, where overloading a single agent with the system prompts, tools, and MCP servers can overwhelm the AI model. Generally, each agent is designated to specialize and perform one specific task. This architecture can guarantee a more modular and conform to the Principle of Least Privilege by giving each agent the most minimal tools it needs to successfully complete its task. 

Configuring Edbot requires working with an agentic architecture due to its variations with student input and multi-step decision-making processes to generate its response. Our learning tool is not expected to perform under pre-defined tasks. The planning and execution steps of the agent depends entirely on the needs and requests of the student interacting with the chatbot interface, encouraging the use of an agent versus a non-autonomous program. 

The expected behavior of Edbot can also be broken down into two concrete decision-making steps: evaluating the student’s mastery level of a subject and generating the questions to return to the student. It’s important to keep these two responsibilities of the agent in mind, since the control group of the study will not have access to the former skill; the agent will skip the step to reason the student’s understanding-level and give a general question to the user. The requirements for two distinct subtasks under a modular system suggests the use of a multiagentic system. By configuring agents to specialize in these two forms of autonomous behaviors, the system can avoid overflowing the context window by keeping independent system prompts and tool descriptions for each. Single agents would have to not only decide whether this query comes from the control or experimental group, but also manage the available tools and context for each step of the question-generating process.

#### Agent architecture patterns 

Multi-agent systems can be broadly divided into two main architectural patterns: centralized and decentralized architectures. A centralized pattern is characterized by an “orchestrator” agent that breaks down tasks to specialized worker agents. The orchestrator relies on an AI model to dynamically route its sub-tasks to pre-configured subagents, depending on the goals of the query. An orchestrator-agent architecture becomes useful when complex tasks require specialized knowledge and tools for a specific use case.

A decentralized pattern is collaborative, where autonomous agents work together in a peer-to-peer fashion to make decisions and negotiate roles dynamically. This behavior mirrors the collaborative environment of human teamwork, where agents behave independently but coordinate and communicate amongst each other to dispatch their own expertise while staying consistent on the overall goal.

We also consider agentic workflows, in contrast to centralized and decentralized architectures, which follow a more structured workflow for multi-step processes. They provide less autonomy for agents to dynamically route and delegate tasks to other agents. Agentic workflows are ideal for sequential goals that have predictable execution paths. They perform well in repeatable processes and deterministic behavior, achieving higher accuracy for highly focused tasks.

We prefer a centralized agent architecture over a peer-to-peer design because of the context overhead and number of steps for each student request – analyzing student's responses to check for skill mastery, generating brand new questions, and using tools and MCP servers to access other resources. By separating the main agent for user interaction from the subagents with specific responsibilities, the model can generate more accurate analysis and responses to each step in the agentic pipeline. The pipeline from the orchestrator, to calling subagents and their respective tools, back to the orchestrator is a nondeterministic process. Depending on the student’s query into the chatbot and their requests, whether that be a request to explain a certain concept or to quiz them on a topic, the number of subagents spawned from the interaction varies. Therefore, it’s more reliable to delegate separate tasks to subagents while the main agent stays responsible for processing user messages and deciding what subagents stay relevant to the task.

This approach also guarantees a more modular, structured approach to building Edbot. Since the study intends to use two versions of the tool for the control and experimental groups, delegating subagents for tasks allows the ability to enable or disable the Understanding-Checking subagent. The orchestrator-agent architecture sacrifices higher token usage for its ability to handle highly complex, non-deterministic tasks. Since each subagent is spawned independent of the main orchestrator agent, it must inherit the context from the previous conversations, leading to difficult context management. However, keeping a shared, persistent, memory of student progress, removes the need to constantly pass conversation history to newly spawned subagents.

#### Memory

* Memory compaction: At what point do we want to compact memory and how? We can attach a middleware that configures the memory compaction

Each subagent’s state is completely isolated from the main agent. When the main agent spawns a subagent, the newly created agent does not inherit any of the caller’s conversation history, tool calls, or immediate thoughts. Skills defined in the main agent are not visible to the subagent and vice versa, but tools may be inherited by the subagent unless explicitly configured with `tools=[...]`. However, the runtime context that starts the main agent is shared with the subagent, propagating any credentials, long-term memory store, and the virtual filesystem backend.

The Understanding-Checking agent and Content-Generating agent both require some understanding of the student’s conversation history with the main agent to make their respective decisions. The Understanding-Checking agent must have knowledge of the recent conversation history to analyze a student’s exchange with the chatbot on a certain concept. The Content-Generating agent should be aware of the CS topic currently being discussed and the student’s classification on Bloom’s Taxonomy. 

The first approach is to pass the entire conversation history from the main agent to the respective subagent, giving it all the interactions between the student and the orchestrator. While this guarantees that the full context is within the scope of the subagent, it accumulates in the context window and unrelated messages can blur the content of the main conversation. Summarizing the conversation history has the benefit of occupying less context in the prompt of the subagent, but risks losing important details that could potentially point towards a student’s improvement in understanding. To still preserve the core ideas of the conversation, the Understanding-Checking Agent inherits the 3 most recent back-and-forth messages with the agent. By relying on a fixed number of messages in the conversation history, we can pass down recent context with higher latency and reduced token usage.

Some memory is accessed across all agents in the system, such as the concept being currently discussed and the student’s mastery on the topic. The UCA needs this information to assess whether a student has improved or regressed in their understanding and the CGA uses this context to generate content calibrated at the right level. The simplest design to accomplish this is to thread the context through the interface of every agent call. The main agent, that handles the conversation interface with the user, can hand the information along when it spawns the stateless subagent. This approach fails, since the information is not persistent and cannot be scoped throughout longer conversations where topics are revisited later in the thread. We want an approach where the agent can quickly key a schema for a student and a topic to retrieve their classification level without sacrificing latency and accuracy.

We rely on a shared, persistent memory that exists in the virtual file system of our agent. The memory stores the student model, including the student’s current standing along Bloom’s Taxonomy, keyed by the specific topic. Each agent is kept stateless, but can quickly retrieve the student data it needs at any point in the conversation. Similarly, a question-logging model is kept in the virtual memory for the CGA to store asked questions and its corresponding rubric. The UCA accesses this information to determine whether a student’s response tolerates an update to its classification. 

We adhere to the Information Hiding Principle by allowing only one writer to each of the shared models. Each component’s internal state is only modified by a well-defined interface, where the student model is written by the UCA and the question-logging model is mutable by the CGA. This keeps the model consistent and less likely to be in an unstructured state.

#### Orchestrator Agent

The orchestrator’s skills are deliberately kept to pattern-matching: classifying the intent of the student (new-concept inquiry, practice request, etc) and extracting the CS concept being discussed in the conversation, passing any judgement-related decisions to the subagent. An alternative would have been to allow the orchestrator to make lightweight understanding judgements itself, which would have saved the cost and latency of spawning a new subagent for this purpose. However, this would blur the boundary that makes the UCA reusable and keeps the control condition cleanly decoupled, maintaining a modular structure that’s necessary for the research study. 

The decision whether to invoke the UCA to re-assess a concept or trust the tier already in the student model is implemented as three, independent mechanisms (deterministic intent-based hard triggers, a model-judged flag, and a cadence-based evaluator) rather than a single unified check. This trades added latency against a more valuable signal for the research study. The layered design requires deeper thinking where escalation could be triggered, which costs more than one consolidated check. However, because each mechanism is distinct and independently identifiable, the escalation event can be logged and fine-tuned for the study. This is valuable for both debugging the system during deployment and for research data, letting us ask questions like how often re-assessment was driven by explicit student messages versus signs of growth during a conversation. The alternative was a single, simpler check that bundles triggers like topic switching, wrong answers, and number of turns elapsed into one judgment. Though this approach requires a single check, it does not produce useful information on how the agent made its triggering decision. The layered design keeps this separation as part of the architecture, encouraging it to further weigh its options and explicitly output its decision before returning.

#### Understanding-Checking Agent (UCA)

When the orchestrator agent spawns a new UCA, by default, it does not inherit the conversation history with the user as it begins its analysis on the student. As a result, it does not know the reason why it was invoked. Keeping the UCA blind to its intent trigger, making it a pure function of the concept and evidence of a potential change in understanding, maintains modularity and keeps internal branching logic kept within the orchestrator. The subagent is easier to tune as one coherent unit and we are able to preserve its reusability as its interface.

While this approach maintains the modularity of the subagent, it can lead to misinterpreting the request when first spawned by the orchestrator. A lack of context passed into a weaker model degrades the quality of the output, as the weaker model struggles to repeat the reasoning process of its caller. 

Therefore, the UCA receives both its conversation history and the invocation context explicitly through its interface, informing whether it was called for a practice request or a mid-conversion follow-up so it could weigh the evidence it receives differently depending on the situation that produced it. With this context, the UCA could make more thoughtful decisions; an incomplete answer given during a cold-start probe shouldn’t be interpreted the same way as a tentative answer given for a formal practice question since the student’s intent differs.

#### Content-Generating Agent (CGA)

#### Scope

The CGA is responsible for generating all forms of new content, whether that be to generate a new question, explain certain concepts, or ask probing questions for topics starting at a new tier. Each of these modes represents a different type of AI generation, suggesting the use of separate agents for each mode. Each agent would receive a distinct prompt. For example, generating a new question would require the designated subagent to also spin up a new rubric with the question and store it in the question-interaction log. The idea of spawning new subagents for each distinct content type supports a modular design, as the system prompt is narrowly scoped for a single job.

The accepted alternative is to keep one subagent that handles different types of content generation, represented as different modes. The modes represent a different interface that can be used when calling the subagent. We prioritize a single agent with three separate callable interfaces because they share the same underlying purpose, to generate tier-calibrated generation. 

##### CS-Content Generation

Tailoring the CGA to produce any type of calibrated content was intentional, in contrast to limiting it to only generate new questions. One possible configuration kept the orchestrator agent to handle simple follow-ups and clarifications directly, using existing student-model state to avoid the latency and cost of an extra subagent call for straight-forward content. This would also provide the benefit of cheaper and faster agents calling for the common case of lightweight follow-ups. 

However, we rejected this approach in favor of routing all CS-content generation through the CGA, which is why ‘explain\_at\_tier’ exists as a mode. If some tailored content came from the orchestrator generation, the tailoring would become invisible and unmeasurable during research analysis wherever the orchestrate generated it directly. Centralizing generation in one auditable, tier-aware path keeps every piece of content a student receives consistent between the control and experimental conditions.

##### Cold-Start Probing

For a concept with no prior assessment in the question log model, one approach was to generate content at a fixed default tier and letting normal conversation refine the estimate from there. This path is simple and immediate, and is the preferred method in the control group since there is no UCA available to drive adaptive probing at all.

On the other hand, the experimental group receives the benefit of routing to the UCA for adaptive probing, where the UCA chooses a probe direction and the CGA generates the actual ‘probe\_at\_tier’ content at each step. In particular, we adopt a binary search style of probing along the Bloom’s Taxonomy levels because we can guarantee the results converge on a reasonable starting estimate in 2-3 turns. It’s important to start with a practical starting point to reduce the amount of reasoning that goes in for a student’s early interaction on a wrong assumption. The estimate doesn’t need to be highly accurate, since the escalation trigger continues correcting it afterward, making the extra cost of a short probing sequence worth paying only where a UCA exists to drive it.
